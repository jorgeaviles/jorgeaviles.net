## What I developed

I built an extract-based analytical foundation connecting legacy source information with reusable Python and PySpark preparation, Parquet datasets in Azure Data Lake Storage Gen2, and Synapse serverless SQL access. It supports SQL investigation, aggregated analysis, and selected downstream application queries.

The work began in Python and Jupyter notebooks, exploring questions beyond established reporting. As investigations developed, I turned the preparation into reusable workflows. University consultation informed early modeling proposals; departmental knowledge helped frame what the data could meaningfully explain.

## My role and collaboration

I am the sole hands-on developer of the analytical notebooks and data platform. My responsibilities span transformations, prepared datasets, and SQL access structures. Departmental colleagues contribute practical knowledge of billing and casework, helping me revisit assumptions and refine requirements.

I designed and developed the analytical preparation and SQL access layers, coordinating with IT colleagues on scheduled source extracts, infrastructure access, and application permissions.

## Engineering decisions

**Preserve source relationships.** Some legacy records contain repeated groups of values. Selected transformations preserve positional alignment, retain repeated occurrences, and separate malformed groups for review. Explicit type conversion, deterministic selection for selected projections, and count and uniqueness checks preserve the intended row grain.

**Separate exploration from reusable preparation.** Python and PySpark make preparation explicit and repeatable. A notebook can test an idea; a published dataset needs a declared shape and an access pattern consumers can depend on. Tests check selected transformation and publication contracts; runtime validation checks the prepared data.

**Keep prepared files reusable.** Parquet provides columnar data in ADLS Gen2, available independently of one notebook. Source representations, normalized detail, and serving datasets use layouts suited to their respective roles. The trade-off is maintaining schemas, file layouts, and the relationship between dated snapshots and serving data.

**Provide serverless analytical access.** [Synapse serverless SQL](https://learn.microsoft.com/en-us/azure/synapse-analytics/sql/on-demand-workspace-overview) queries lake data through external tables, views, and selected stored procedures. This serverless access layer makes file layout, query shape, and data scanned important design considerations.

**Validate before publication.** Selected workflows validate prepared results, stage a serving copy, and promote it to a stable location. Extract context, transformation information, and counts help explain what was produced. Orchestration, failure handling, recovery, and analytical validation are part of that publication boundary.

## What the platform enables

Prepared information supports repeatable investigation and selected application queries. The [Audit Portal case study](/work/analytical-applications/) describes the application-facing work. The prepared data also supports bill-level feature engineering and model development. The [machine-learning case study](/work/machine-learning-audit-prioritization/) describes the implemented training, validation, calibration, and scoring pipelines, which remain experimental.

The platform tracks freshness through upstream extract delivery, preparation, and publication. Visibility into those stages helps consumers interpret snapshots and investigate delivery or preparation issues.

## What I learned

Maintaining an analytical foundation means defining what a row represents, recognizing preparation failures, and making consumer assumptions explicit. Domain knowledge and validation make reuse credible as questions and downstream applications change.
