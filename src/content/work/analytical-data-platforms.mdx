## What I developed

I built an extract-based analytical foundation connecting legacy source information with reusable Python and PySpark preparation, Parquet datasets in Azure Data Lake Storage Gen2, and Synapse serverless SQL access. It supports SQL investigation, aggregated analysis, and selected downstream application queries.

The work began in Python and Jupyter notebooks, exploring questions beyond established reporting. As investigations developed, I needed preparation that could be reused instead of rebuilding it for each question. University consultation informed early modeling proposals; departmental knowledge helped frame what the data could meaningfully explain.

## My role and collaboration

I am the sole hands-on developer of the analytical notebooks and data platform. My responsibilities span transformations, prepared datasets, and SQL access structures. Departmental colleagues contribute practical knowledge of billing and casework, helping me revisit assumptions and refine requirements.

IT colleagues helped establish scheduled source extracts and infrastructure access. Those contributions are separate from development: I did not design every upstream source system or independently administer the organization's Azure environment.

## Engineering decisions

**Preserve source relationships.** Some legacy records contain repeated groups of values. Selected transformations check positional alignment and separate malformed groups for review; flattening groups independently could manufacture relationships. Repeated occurrences are not automatically errors. Explicit type conversion, deterministic selection for selected projections, and count and uniqueness checks preserve the intended row grain.

**Separate exploration from reusable preparation.** Python and PySpark make preparation explicit and repeatable. A notebook can test an idea; a published dataset needs a declared shape and an access pattern consumers can depend on. Selected transformation and publication contracts have tests, while runtime data validation remains a separate responsibility.

**Keep prepared files reusable.** Parquet provides columnar data in ADLS Gen2, available independently of one notebook. Source representations, normalized detail, and serving datasets have different logical responsibilities without requiring an identical physical layout everywhere. The trade-off is maintaining schemas, file layouts, and the relationship between dated snapshots and serving data.

**Provide serverless analytical access.** [Synapse serverless SQL](https://learn.microsoft.com/en-us/azure/synapse-analytics/sql/on-demand-workspace-overview) queries lake data through external tables, views, and selected stored procedures. It is not a dedicated provisioned SQL warehouse. File layout, query shape, and data scanned still affect how consumers use this layer.

**Validate before publication.** Selected workflows validate prepared results, stage a serving copy, and promote it to a stable location. Extract context, transformation information, and counts help explain what was produced. This boundary adds orchestration, failure handling, and recovery work; a successful write alone does not prove analytical correctness.

## What the platform enables

Prepared information supports repeatable investigation and selected application queries. The [Audit Portal case study](/work/analytical-applications/) describes the application-facing work. The prepared data also supports bill-level feature engineering and model development. The [machine-learning case study](/work/machine-learning-audit-prioritization/) describes the implemented training, validation, calibration, and scoring pipelines, which remain experimental.

Freshness depends on upstream extract delivery, preparation, and publication rather than a real-time connection to the operational database. Keeping those stages visible helps investigate stale or incomplete results. No measured accuracy, query-speed, cost, financial-return, or guaranteed freshness improvement is claimed.

## What I learned

Maintaining an analytical foundation requires more than writing a query: it means defining what a row represents, recognizing preparation failures, and making consumer assumptions explicit. Domain knowledge and validation make reuse credible as questions and downstream applications change.
